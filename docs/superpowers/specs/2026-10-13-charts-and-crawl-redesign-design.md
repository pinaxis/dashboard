# Charts interactivity and crawl-run redesign

**Date:** 2026-10-13
**Status:** approved design, pre-plan
**Repos touched:** `dashboard` (primary), `pinaxis` engine (telemetry only)

## Goal

Make the private Charts view interactive and data-rich, completely redesign the
Crawl view so it reads well and shows a run's real lifecycle (including the
GitHub to Google Cloud Run handoff), and add cheap engine telemetry so the
handoff view carries live per-turn numbers after a future crawl.

## Why

The Charts view is five static horizontal-bar panels; the 54k-node private
document already carries per-node `firstSeen`/`lastSeen`, `severity`, `band`,
`category`, `valid`/`validated`, plus `credentials` and `coOccurrence`
aggregates, none of it explored over time or cross-filtered. The Crawl view is
a plain table that does not convey that a crawl physically chains turns across
hosts (GitHub Actions and Google Cloud Run Jobs), and it looks unfinished.

## Ground truth (from the engine)

A crawl run is one or more **turns**. One turn's real code phases, in order:
`Start (FRESH/CONTINUE/STOPPED) -> Lock acquire + heartbeat -> Download dataset
-> Seed frontier -> Search sweep (64 workers over a weighted frontier) ->
Validate (live, per-target endpoints + rate limits) -> Store graph (nodes/edges)
-> Enrich (contributors/social) -> Snapshot + flush/upload -> Offload decision
-> Hop to the next host`. Hosts rotate: `GitHubHost` dispatches `scan.yml`;
`GcpHost` runs a Cloud Run Job via `run.googleapis.com/...:run`; `Local` seeds
on a dev machine. The handoff is real.

What the dataset persists today: node/edge tables with `first_seen`/`last_seen`/
`severity`, a `pending` frontier table (`source,target,query` only), and
`validity_cache`. What it does NOT persist: any run/turn/stage/event table, no
per-stage timing, no per-target run counts, no host/chain record. Per-run signal
that leaves the engine today: GitHub Actions run metadata (`createdAt`,
`conclusion`, `url`), two step outputs (`offload`, `pending`), and stdout `[scan]`
log lines. The dashboard's `build-graph` derives a per-run `stored` count by
bucketing node `first_seen` between run starts.

**Consequence:** a truthful GitHub-to-GCP per-turn pipeline needs the engine to
emit host/chain/counts. Until then the dashboard can show the architecture-true
lifecycle annotated with the counts it does have, without inventing per-stage
numbers.

## Global constraints

- Do not run a crawl. It rebuilds the dataset from a blank DB and overwrites the
  preserved 54,014-node dataset.
- The private 54k asset (`dist-private/api/graph.json`) and the catalog are not
  regenerated by this work.
- Tested logic lives in `.ts` modules; `node --test` strips types but does not
  transform JSX, so no tested logic in `.tsx`.
- recharts 2.15.4 (already a dependency) is the charting library; feed it
  aggregated series (daily buckets, top-N), never the raw 54k nodes.
- Charts and Crawl are private-view only (`mode === "private"`).
- Commit as finn@birich.de. No en-dashes or em-dashes anywhere. Conventional
  Commits.
- The engine schema touch is backward compatible: the current dataset (schema 5,
  no per-turn record) still loads and renders.
- Comments: default to zero; only non-obvious *why*.

## Part A: Charts view

### Data (new module `src/data/chartSeries.ts`, tested)

- `exposuresOverTime(document, bucket: "day" | "week"): TimePoint[]` where
  `TimePoint = { at: string; found: number; critical: number; cumulative: number }`.
  Built from each node's `firstSeen`; `critical` counts nodes whose `band` is
  `CRITICAL` first seen in that bucket; `cumulative` is a running total of
  `found`.
- `byCategory(document): Bar[]` - SECRET nodes grouped by `category` (null folded
  to `"uncategorized"`), descending.
- `byFileType(document): Bar[]` - FILE nodes grouped by the extension of `path`
  (no extension folded to `"other"`), descending, top 12.
- `validityTotals(document): { live: number; dead: number; formatOnly: number }`
  summed from `stats.credentials`.
- `applyFilter(document, filter): GraphDocument` - returns a shallow document
  whose `nodes` and `stats`-derived inputs are narrowed to the active slice.
  `filter = { bands: Set<Band>; types: Set<NodeType>; validity: Set<"live" | "dead" | "format"> }`.
  Empty set in a dimension means "all". Validity applies to SECRET nodes via
  `valid`/`validated`; non-secret nodes pass the validity dimension.

### Component (`src/components/Analytics.tsx`, presentation only)

- A cross-filter control bar (reuse the existing `Chips` component) for severity,
  type, validity. Selection held in `Analytics` state; all series recompute via
  `useMemo` against the filtered node set.
- Panels, using recharts where interactivity helps:
  - **Exposures over time** - `ComposedChart`: bars for `found`, line for
    `cumulative` critical. Day/week toggle. Tooltip with exact counts.
  - **Validity** - recharts `PieChart` donut (live/dead/format), hover detail.
  - **Severity distribution** - interactive bars, click a band to toggle it in
    the cross-filter.
  - **Credentials by type** - keep the stacked segmented bars (already good),
    made clickable to the type drawer (already is).
  - **By category** and **By file type** - new bar panels.
  - **Most exposed repositories** and **Types that leak together** - kept,
    bars clickable where a drill-down target exists.
- Drill-down: clicking a repository bar opens that node (via `onOpenType` style
  callback extended to nodes where meaningful) or the type drawer for a type.
- Hover tooltips on every recharts surface.

### Error/empty states

Each panel renders the existing `.empty` message when its series is empty. The
time chart shows an empty state when no node carries `firstSeen`.

## Part B: Crawl view

### Data (`src/data/crawlAnalytics.ts`, extended, tested)

- `lifecycleStages(): Stage[]` - the static, architecture-true stage list with
  `{ key, label, host: "github" | "gcp" | "either", note }`. Pure constant +
  shape, unit-tested for order and host tags.
- `runSpan(crawl): { first: string | null; last: string | null; turns: number }`.
- Keep `targetProgress`, `throughput`, `queueBySource`.

### Component (`src/components/CrawlProgress.tsx`, redesigned)

- **Pipeline panel** (new `src/components/CrawlPipeline.tsx`): renders
  `lifecycleStages()` as a horizontal flow with a visible GitHub to Google Cloud
  Run handoff. Annotated with real aggregate counters (searched/stored/pending
  from `throughput`), clearly separated from the architectural stage labels. When
  per-turn telemetry exists (Part C populated), stages show live per-turn numbers;
  otherwise they show the architectural description only. No fabricated per-stage
  timings.
- **Run timeline**: redesigned from the plain table into a vertical timeline,
  newest first, each run a card: when, `scan`/`resume` badge, conclusion color,
  found-per-run bar, "view run" link.
- **Per-target progress** and **Queue by source**: restyled into the new card
  layout; priority editing table kept as is behaviorally.
- Controls panel kept behaviorally, restyled.

### Styling (`src/index.css`)

New card/section styling for the crawl stage; a legible pipeline graphic
(nodes + connectors, the GCP hop visually distinct); timeline styling. No change
to the graph or public view.

## Part C: Engine telemetry (pinaxis repo)

Backward-compatible additions so the pipeline can later show live per-turn data.

- Extend `Scanner.RunOutcome` with `host` (from `Env`/host detection),
  `chainDepth`, and `perTarget: Map<String, { searched, stored }>`. The counters
  already exist as `AtomicInteger`s in `Scanner`.
- Extend `GitHubClient.publishOutputs()` / the `ScanCommand` call site to emit
  `host`, `depth`, and a compact per-target JSON to `$GITHUB_OUTPUT`.
- `build-graph`'s crawl block gains an optional `turns: TurnRecord[]` array
  (host, depth, conclusion, at, perTarget) assembled from workflow run metadata +
  step outputs when available. Absent on the current dataset; the dashboard
  treats `turns` as optional.
- Schema stays 5 where the node/edge shape is unchanged; the crawl block simply
  carries an optional new field. The dashboard's `Crawl` type gets an optional
  `turns?: TurnRecord[]`.

**This data only populates on the next crawl, which this work does not run.** The
view ships correct with `turns` absent and upgrades itself when a crawl later
emits it.

## Testing

- `test/chart-series.test.mjs`: `exposuresOverTime` bucketing + cumulative,
  `byCategory` null folding, `byFileType` extension parsing + "other" fold,
  `validityTotals`, `applyFilter` for each dimension and the empty-set-means-all
  rule.
- `test/crawl-analytics.test.mjs` (extend): `lifecycleStages` order + host tags,
  `runSpan`.
- Engine: a unit test that `RunOutcome` carries per-target counts after a
  simulated sweep, and that `publishOutputs` serializes them; golden-friendly.
- Full suite green; `tsc --noEmit` clean for app and worker.

## Review focus (inputs the tests must pin)

- A node with a missing or malformed `firstSeen` must not crash
  `exposuresOverTime` (skip it, do not throw).
- A FILE node whose `path` has no extension or no `path` at all folds to
  `"other"`, never `undefined`.
- `applyFilter` with every dimension empty returns the full set (all nodes),
  not the empty set.
- A crawl with zero runs renders the pipeline (architecture) and an empty
  timeline, no divide-by-zero in throughput.
- A `turns` field absent (current dataset) renders the pipeline in
  architecture-only mode, not a broken "undefined" view.

## Out of scope

- Running a crawl.
- Changing the public view, the graph view, or the login/worker gating.
- Parsing stdout `[scan]` logs (telemetry comes from structured outputs instead).
